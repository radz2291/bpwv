# Architecture

## Baseline: 24 October 2026

The initial folder contained only `BorderPoint_Weave_Setup_v1.zip`, with prompts, model notes, references and a workflow connection map. It is preserved byte-for-byte and is not loaded into engine logic. There was no Git repository or prior application. No VICT Studio code or dependencies were reused.

The application uses Svelte 5.57.2, SvelteKit 2.70.3, Svelte Flow 1.7.0, TypeScript 5.9.3, Vite 7.3.7, Zod 4.6.7 and adapter-node 5.5.7, with an npm lockfile. Node is 22.22.3. Registry metadata and installed peer dependencies were inspected. Svelte Flow 1.7 requires Svelte ^5.25; this combination passes type checking and production compilation. The newest SvelteKit 3 stack changes configuration and library aliases; this first milestone uses the established Kit 2 interfaces. `npm audit` reports three low severity findings in that dependency chain; this loopback-only milestone does not use enhanced form actions or prerendering. Reassess and migrate before deployment. No force-fix was applied.

## Boundaries

- `src/lib/contract.ts`: versioned workflow schema, node definition contract, typed ports, states and registry. JSON parsing is checked with Zod. Node configuration and runtime values are checked by definitions and the engine.
- `src/lib/registry.ts`: seven node definitions, including Stage 2 Reference Set v1. Definitions own configuration validation, input/output metadata, defaults, handlers and optional pure media projection. UI cards use this metadata. New handlers register through `NodeRegistry.register`; duplicate kind/version pairs fail. Registry plugins are trusted source modules, not arbitrary executable JSON imports.
- `src/lib/engine.ts`: graph validation and dependency execution. No initial-node-specific dispatch. Checks identity, ports, one incoming edge per port, cycles and group membership. Executes deterministic DAG dependencies once per run. Validates runtime port values and output types; failures block dependents but not unrelated branches. No loops, scheduler, parallel paid calls or automatic retries.
- `src/lib/server/provider.ts`: replaceable `ProviderAdapter` interface and the initial Codex/Weave request adapter. Engine receives a callback, independent of bridge transport. Switching providers requires registering/wiring an adapter at the server composition boundary, with no engine changes. Models are discovered snapshots, not universal hardcoded settings.
- `src/lib/server/store.ts`: additive SQLite initialization and shared connection; WAL, busy timeout, workflows, run snapshots, requests and origin asset metadata. `data/assets/` contains local media; `data/requests/` contains initial pending request exports. SQLite is authoritative for later status updates.
- `src/lib/server/workflow-service.ts`: sole workflow authoring service for node discovery, create/get/save, atomic ordered graph changes, validation/readiness, revisions, URLs, execution retrieval and asset associations. Mutations run under `BEGIN IMMEDIATE`; failed batches roll back graph edits and asset deletions. The service accepts an injected database/registry for isolated tests. Removed nodes lose current asset associations; immutable run snapshots retain history. Full editor saves and MCP mutations use the same revision checks.
- `src/routes/api`: thin local adapters to the shared workflow service, plus separate media upload/read and Weave result reporting. `src/routes/+page.svelte` projects the same records into Svelte Flow and opens `?workflow=<id>` links returned by agents. It previews associated assets and refuses stale saves after concurrent MCP changes.
- `src/mcp/server.ts`: transport-independent tool registration with sixteen typed tools and annotations, six available to read-only clients. It calls the same service directly, without requiring a visual server, Codex or a model. `src/mcp/stdio.ts` uses explicit local write grants; `src/mcp/http.ts` provides authenticated loopback Streamable HTTP. `scripts/mcp-launch.mjs` resolves the workspace from any host working directory. `MCP_SETUP.md` documents local authorization, official Inspector evidence and the future supported ChatGPT connection boundary.

## Execution and provider boundary

Stage 2: local definitions can expose a pure `project` handler for media display before a run. `media-view.ts` follows typed connections using those handlers or actual completed run outputs; it never invokes generation. Media frames preserve aspect ratio and provide inspector/lightbox enlargement. `executionSignature` excludes cosmetic positions/labels and revisions, allowing compatible result restoration after a save while invalidating changed configuration or wiring. Selected execution targets run only their dependency closure; the editor prepares the initial generation plus its Preview by default. Refinement is separately initiated.

Discovery now loads a provenance manifest (`evidence/weave-model-catalog.json`) containing genuine original Flux and new Nano Banana 2.1 snapshots. Nano's discovered `images` limit is 14; settings are model-specific. RequestService records exact local-ID → actual uploaded-object mapping and provider-input hash before an actual quote. A recorded quote/structured decision is audit metadata, never a model invocation or independent approval authority. The official external tool still enforces its own explicit cost acknowledgement. Quotes >=5 stop. Original request input, prompt, workflow revision/hash and node snapshot remain immutable. Returned output association IDs are local identities when the provider supplies only a URL; prediction IDs and URLs must be actual provider returns.

The approved Stage 2 run cost 3.5 credits after the user's structured approval and produced a real initial image. Its Preview completed through the existing deterministic continuation; refinement remained idle. See `evidence/stage2-request-proof.json`. No automated test calls a model. This concrete run replaces the earlier untested-generation limitation below for this one configuration; it does not establish support for every discovered model or visual acceptance of the artwork.

Text, Combine, Asset Input, Preview and Refinement execute without models. Weave Model validates against its selected discovered contract, freezes the full prompt, parameter input, contract, hash, lineage and run context, then enters `pending`. Its Preview is `blocked` until actual output arrives. The application never fabricates success. Codex processes the request through its authenticated Figma MCP, obtains the actual quote and user approval, then reports the actual prediction and model ID. The local application cannot invoke that authenticated MCP independently. No API keys or independent Weave client are configured.

Model discovery from 24 October is preserved verbatim in `evidence/weave-discovery.json`. Flux 2 Pro accepts up to eight images; Flux 2 Dev LoRA has one image input plus LoRA fields. Settings and validation are generated from each contract. Snapshot data must be refreshed via Codex before a paid run. The UI labels cost as an estimate. The proof model choice is a structural fixture choice, not authorization to generate. No account-credit balance was asserted.

Input `assets` represents multiple references for ONE model call. It never means iterate or run a batch. Planned iterator nodes will use separate array ports, child-run identities, scheduling and approval/budget semantics. Asset Input outputs one asset; Reference Set v1 appends it after optional existing references without changing identities or lineage. Models with required fields outside the available prompt/reference flow must be configured with valid fields or execution fails; no silent input conversion.

## Reuse and refinement

Workflow groups are versioned templates referencing stable node IDs. The editor can capture a selection and insert copies with fresh node/edge identities and internal topology preserved. External connections are deliberately not copied. Nested groups, exposed group ports, a separately published group library and executable subgraphs are planned.

Every persisted run contains the whole graph and its configuration; every generation request contains an immutable prompt snapshot/input hash. Refinement consolidates human feedback into one deterministic prompt successor; it does not silently call an LLM or replace history. Planned review/LLM nodes can produce structured feedback for a later refinement pass. Branch/compare UI and formal feedback attribution remain planned.

## Limitations

The visual application is single-user and loopback-only, without UI authentication. The separate MCP HTTP facade requires independent local read/write bearer credentials, validates Host/Origin and never exposes the UI API as its transport. Stdio trusts the operator's process/OS grant. Hosted OAuth and multitenancy remain future deployment work. The existing local server is connected through OpenAI Secure MCP Tunnel; ChatGPT registration was completed by the user. Authoring itself is independent of any specific AI host. Save is explicit; last-run state restores when execution inputs/topology still match. Source and local media remain on this computer; the actual generated result currently uses its returned provider HTTPS URL and depends on its continued availability. Asset metadata includes origin IDs and declared provenance; authoring an association does not prove external generation or approve a charge. The separate Weave result endpoint records returned assets against originating nodes. Content sniffing/transcoding and authenticated external result signatures remain future work. The Stage 2 approved Nano run was inspected, while other model combinations remain unverified.

## MCP compatibility and verification

The official SDK 1.32.2 maintenance line implements MCP 2025-11-25 and was verified with official Inspector 2.12.0 through initialization, discovery and actual tool calls on stdio and Streamable HTTP. This is not a claim of MCP 2026-07-28/v2 SDK support. Both successful typed results and structured error responses are tested; tool annotations are advisory metadata, not permission enforcement. Inspector reports zero schema-portability errors, with warnings about intentionally open extensible JSON configuration fields. No model call or API key is needed for local authoring or deterministic execution. `execute_local` rejects all generative graphs rather than entering the separate provider path.

The official Inspector end-to-end proof builds and persists a complete local text graph, verifies batch rollback and conflict handling, associates actual imported media, and reopens through separate sessions. Browser verification proves bidirectional UI/MCP edits and stale-save rejection. A further Inspector proof performs authoring and local execution while the visual server is stopped and the launcher runs from another working directory. Evidence is under `evidence/mcp-*.json`. The subsequent Secure MCP Tunnel connection is recorded in evidence/chatgpt-tunnel-connection.json: ChatGPT registration was user-completed, all sixteen plugin tools are available, and connected discovery/list/reopen read calls succeeded. This does not replace the separate write-test or paid-generation evidence.

Compatibility sources: [official MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk/tree/v1.x), [official Inspector](https://modelcontextprotocol.io/docs/tools/inspector). The ChatGPT connection options and current boundaries are sourced in MCP_SETUP.md.

`tests/engine.test.ts` registers a separate test-only node to prove extension without engine edits. It is separate from the seven production nodes and is not a simulated generation capability.
