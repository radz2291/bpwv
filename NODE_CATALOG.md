# Node catalog

Six initial nodes are the first milestone, not the product boundary. This is an architectural roadmap inspired by Weave's major families, not a claim that the connector exposes every listed node as a direct model. Status vocabulary: **Implemented** = working local behavior; **External-dependent** = bridge implemented, real generation needs external provider/approval; **Planned** = documented, not executable; **Simulated** = test fixture only. No product nodes simulate generation.

Ports are named and typed in a common versioned registry. Unless stated otherwise, planned versions begin at v1 when implemented. Planned providers listed below are design intent and require actual discovery/verification, not an asserted connected service. Registry contracts must be shared by editor, validator, execution and agent interface.

## Extension acceptance

1. Register a unique kind/version with typed ports, config validation and execution handler.
2. Add its configuration editor or use a future schema-driven configuration renderer; do not change core graph traversal.
3. Verify JSON round-trip, incompatible port rejection, required inputs, deterministic/model boundary, error states and lineage as appropriate.
4. Register a provider adapter at the server composition boundary when required. Importing workflow JSON cannot install executable code.
5. Keep batch iteration separate from reference conditioning: eight images passed to one Flux 2 Pro call means one conditioning input, not eight jobs.

The extension unit test executes a newly registered handler with no changes to core execution. Additional production nodes remain planned until their own behavior and dependencies are verified. Node settings are driven by discovered Weave contracts, with discovery provenance/date retained. This milestone does not claim the complete Weave node library or an end-to-end paid run.
